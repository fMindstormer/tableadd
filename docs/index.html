Full adder i works in row i + 1. In that row the cell in column si is orange when sum bit i is 1 and dark when it is 0; the ringed cells are the answer, with the final carry under c. The page's script only writes the first row and reads the result back by measuring where cells landed; the arithmetic happens in layout.

What the browser does

Each row places its cells from left to right, each in the first slot that no taller cell from an earlier row still covers. That rule is the HTML standard's table forming algorithm, and it is all this table uses: every cell is one column wide, so cells never overlap and there is nothing for engines to disagree on.

In each row a free column learns exactly one number: how many free columns lie to its left, because that decides which of the row's cells lands on it. The repeated row is therefore a lookup table from that count to a rowspan.

Ten cells. A column that is free with 3 or 5 free columns to its left gets a cell one row tall and is free again in the next row. Every other free column gets a cell that covers it to the bottom; browsers clamp the 999.

One full adder, six columns

A bit is a pair of columns. In the row where it is read, exactly one of the two is free: the left one for 1, the right one for 0. Everything outside the pair counts it as one free column either way. Only columns between the two count the bit itself.

Six reader columns sit inside the pairs for a, b and the carry, so each counts s = a + b + carry plus its own position, and the repeated row answers for it.

The next full adder sits between R2 and R3. In its row it counts the free columns to its left, and of those only R1 and R2 can vary: together they are the carry. The nesting is the wiring.

Where it works

Six engines lay out all 512 four-bit tables (with and without carry in), 200 random eight-bit tables and 60 random twelve-bit tables with every cell in exactly the slot the specification gives it:

  • Chromium 141: Blink, the engine in Chrome and Edge
  • Firefox 159: Gecko
  • Safari 27: WebKit, in Safari itself
  • WebKitGTK 2.52: WebKit, the engine Safari is built on, in its Linux port
  • wkhtmltopdf 0.12.6: a WebKit from 2016
  • WeasyPrint 70: a table layout written in Python

The readout above is measured in your browser, so opening this page checks whichever engine you use.

What identical rows can and can't do

  • Alone, they settle. When the repeated row is itself a short pattern (two to five cells over and over, rowspans one to four), every such row turns a random first row into a layout that repeats every 12 rows or fewer. Information only travels rightward, so disturbances drift off the edge.
  • Two natural counters are impossible. If a cell's free count is a multiple of the row's period, every position of the count looks the same to it. And cells that wake in turn can only push their state one way.
  • Scans work. A reader has to sit inside the pairs it reads, so information flows inward, from the outside of the nest to its middle. That suits a chain like this adder, which reads the bits in order and passes on a carry. Subtraction and comparison need no new parts: swapping the two columns of b’s pairs inverts it, so the adder with carry in 1 works out a − b, and its carry out says whether a ≥ b. Multiplication works too, column by column, but its repeated row grows with the width. One fixed row of three cells, with rowspans 999, 2 and 3, is enough for the parity and the inner product mod 2 of any number of bits. With rowspans 0, 2 and 6 (a rowspan of 0 lasts to the end of the table) it computes any formula, by Barrington’s theorem, so one fixed row multiplies too, in tables of polynomial size. Each position’s count of free columns evolves on its own, so no result is ever shared between two places. Whether identical rows can compute without a bound is still open.
